Ongoing research

Procedural Memory Lab

  • Python
  • pytest
  • language models
  • experimental evaluation
  • causal verification
View the code on GitHub

Independent research on a precise question: does a small language model really improve when it retrieves a procedure written in earlier attempts, or does it only need to see a similar answer again? To tell the two explanations apart, every task (Python functions with real bugs, checked by pytest) is run in four configurations: a larger model, a small model as the baseline, a small model with a general procedure retrieved, and a small model given the solution of a similar case.

Key findings

  • In the first five complete runs the procedure library finished ahead of the baseline every time, with 7.8 percentage points more accuracy over 116 attempts. The result is encouraging but not conclusive: the runs are not independent replications and the library changed over time.
  • In the largest early run only two of the ten covered patterns paid off. An overall improvement is not enough to justify every single procedure.
  • Causal check: changing a value inside the retrieved procedure made the answer follow it 12 times out of 12, while changing an unrelated value had no effect (6 out of 6). The model chose the right rule but recited a value.
  • After rewriting the procedure to ask for a derivation, the model computed tolerances across seven orders of magnitude.
  • Cost: using a ready made procedure costs on average 116 to 343 more input tokens than the bare model, while building a new one costs about 1000 to 2000 tokens once per pattern.
  • The same ideas were carried over into Aria, a study app for a real user with ADHD, as a second testing ground. In real use a comparison between groups has a composition bias, so a blind paired comparison is used. On 22 comparable pairs with a local model, retrieval scored 17 of 22 against 13 of 22 for the bare prompt, a result that is not conclusive yet.

How to run it

  1. Python 3.11 or newer and the dependencies listed in requirements.txt are required.
  2. The guided setup is started with python -m cognitive_rpg.settings_wizard.
  3. The experiment is launched with python -m cognitive_rpg.experiment.experiment_0. Mock adapters are available to develop without paid calls.

An independent research project, not a peer-reviewed paper. The code is visible for evaluation; reuse is not permitted.

University project

VinylWaves

  • Java 21
  • Jakarta Servlet and JSP
  • MySQL
  • Maven
View the code on GitHub

A Java web shop for vinyl records, CDs and turntables, developed by a team of three for the Web Software Technologies course. It includes a catalogue with search and filters, accounts, cart, orders and product management.

How to run it

  1. Import the vnl_db.sql schema into MySQL and set up the local connection expected by the DAO layer: credentials are not in the repository.
  2. From the vnl folder run ./mvnw package to build the WAR file.
  3. Deploy the WAR to a Jakarta Servlet compatible container, for example Tomcat 10.

Team project: each contribution is credited in the README. The code is visible for evaluation; reuse is not permitted.

University project

JustInTime

  • Java 23
  • Spring Boot
  • Thymeleaf
  • JavaScript
  • MySQL
View the code on GitHub

An academic project developed by a team of four: a turn-based card game with a timer, for two to four players. It includes registration and login, matches with special cards, local and global leaderboards, achievements and feedback, with the project documentation (RAD, SDD, ODD).

How to run it

  1. Java 23 and a local MySQL server are required. The justintime database is created automatically; the user and password are set in application.properties.
  2. From the ProgettoIs JustInTime folder the application is started with ./mvnw spring-boot:run.
  3. The game opens in the browser at the address printed by Spring Boot, normally http://localhost:8080.

An academic team project, like VinylWaves. The original repository belongs to a teammate and this is my fork. My contribution is mostly the server-side match logic: turns, session, player state, podium and account deletion.

In development

ASES, Architecture and Software Evidence Scanner

  • Python
  • code analysis
  • software architecture
View the code on GitHub

A scanner that reconstructs what a codebase actually does before recommending how it should change: it classifies the files, collects facts, keeps counter-evidence and only then infers. It analyzes Java, Python, TypeScript and frontend projects.

How to run it

  1. Python 3.11 or newer and an active virtual environment are required. From the repository root: python -m pip install -e "./runtime[documents]".
  2. The interface opens in the browser with ases ui, or a project is analyzed from the terminal with ases scan /path/to/project --out current.ases.
  3. To compare a new analysis with the previous one: ases scan /path/to/project --out next.ases --baseline current.ases.

A personal project still in development. The code is visible for evaluation; reuse is not permitted.
